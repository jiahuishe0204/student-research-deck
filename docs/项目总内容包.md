# 调研交付台 · 项目总内容包

本文件是项目的总入口和长期记忆。已经确认的产品规则、工程问题、提示词变化、界面风格、验收结果和能力边界，都必须在这里登记并链接到具体实现或专题文档。后续不得只修改单份样本、单个页面或聊天中的临时方案而不更新本内容包。

## 一、当前产品结论

- 产品面向生命科学课程、组会、初步科研调研和答辩准备。
- 用户只需输入研究主题；宽题先由系统给出方向，再由用户确认焦点。
- 首版交付包括完整调研报告，以及含上屏文字、配图建议、来源和专业讲稿的 PPT 逐页内容包。
- 报告与 PPT 使用同一证据底稿；重要事实应可追溯，无法确认的内容必须降级或删除。
- 当前公开网站是界面与交付样本演示，不代表真实线上生成、登录、支付和任务持久化已经开放。

## 二、已确认的界面风格

视觉与交互的完整规则见[界面视觉一致性规则](界面视觉一致性规则.md)。当前基线为：

- 暖白—浅紫的低饱和度背景，白色内容卡片，中等紫色作为强调色。
- 大标题使用宋体类衬线字体，正文和控件使用清晰的无衬线字体。
- 首页、题目确认、任务过程、交付结果和图源页面属于同一套设计系统。
- 二级目录采用浅紫柔光渐变、轻微阴影和滑动；不使用拥挤的左侧紫色竖线。
- 桌面与平板的四步流程平均分为四个等宽模块，手机才改为单列。
- 快速版与深入版价格卡片的底部价格信息保持单行，不拆成上下两层。
- 首页 PPT 预览的“问题／路线／证据”必须真实可切换，并同步更新内容、讲稿和来源。
- 品牌图标统一使用紫底白色打开书页图标。
- 首页、交付结果与执行版图均使用同一套浅紫视觉基线，不保留旧绿色客户可见页面。

## 三、已确认的内容生成规则

### PPT目录短标题

- 正文标题与目录短标题分离；工程字段为 `navigation_title`。
- 目录标题一般为 4—12 个汉字，以自然、可区分为准，不机械凑字数。
- 使用高校答辩、组会和学术会议 PPT 的自然表达，避免报告式和 AI 式并列长词。
- 后续工作页面直接使用“展望”；确实同时承担总结时才用“总结与展望”。
- 具体规则位于 `prompts/P6-ppt.md`，终稿继承规则位于 `prompts/P9-final.md`，协议位于 `schemas/P6-ppt.schema.json` 与 `schemas/P9-final.schema.json`。

### 配图与图源

- 能定位原图时，明确写出 Figure/Fig. 编号、分图和用途。
- 无法确认具体图号时，不写“需补充图源”，而是给出可执行的“推荐自行绘制……示意图”。
- 推荐链接供用户判断和使用，不等于系统已经复制、嵌入或取得复用许可。
- 客户文字不使用“不使用未经许可的原图”等防御性后台措辞。

### PPT讲稿与证据边界

- 讲稿采用正式、自然、可直接说出口的学术答辩语域。
- 审计语言留在证据与核验记录；只有影响理解的限制才进入讲稿。
- 页面标题、上屏文字、配图、讲稿和来源必须保持同一证据边界。

## 六、强制同步流程

每次完成用户确认的修改后，依次执行：

1. 判断修改属于当前样本特例还是产品通用能力。
2. 通用能力写入对应提示词、协议、代码、样式或产品决策文件。
3. 新发现的工程问题写入专题复盘；稳定结论在本内容包登记。
4. 增加或更新自动测试，并运行与改动范围匹配的回归。
5. 扫描密钥、凭证、私人数据和不适合公开的原始产物。
6. 将安全的代码、文档、规则和测试提交到 GitHub。
7. 若修改 `web/`，等待 GitHub Pages 成功并检查公开页面。
   - GitHub Pages 默认可能对旧首页缓存约 10 分钟。发布验收先使用带版本查询参数的首页地址，再检查无参数根地址；不能只因新交付页已更新就推断首页缓存也已刷新。
8. 向用户明确说明：改了当前样本、工程规则还是两者；是否已经同步 GitHub；哪些内容因安全边界只保存在本地。
