# 线上 P8 预算阻断根因

记录日期：2026-11-16  
调查对象：`TASK-70d2cf9a7ecf`，腾讯云函数 `research-task-worker-v2`，广州 `default` 命名空间，`$LATEST`

## 已确认根因

导致 17 个 P8 作业最终进入 `permanent_failed` 的直接原因是共享 Tokens 预算阻断，不是邮箱登录故障。P8 调用账本另有 `rejected`、`empty_output` 和 `truncated` 状态；这些输出异常是否对应这 17 个终态失败作业，需要逐请求关联后确认，不改变日志已证实的最终阻断原因。腾讯云 SCF 日志在失败时段直接记录：

> `TASK_WORKER_ERROR ModelBudgetExceeded: 任务下一次请求将超过共享总 Tokens 上限 3000000`

查询时间为北京时间 2026-11-14 13:05—14:25，覆盖 Neon 作业表中最早至最晚的失败时间。此前仅查 14:00—14:25 的日志漏掉了前段，不能据此认定日志里没有根因。

Neon 对应任务的用量账本显示：

- 已结算实际 Tokens：2,920,087
- 仍保留的 Tokens：75,368
- 合计计入预算：2,995,455
- 任务上限：3,000,000
- 当时剩余预算：约 4,545 Tokens
- 已结算实际费用：¥8.573059
- 保留费用：¥0.511957
- 合计计入费用上限：¥9.085016（¥10 上限剩余约 ¥0.914984）

该错误文本表明下一次 P8 请求在共享 Tokens 预算预留处被拒绝。日志明确给出了预算类别和 300 万上限，因此费用上限不是这次异常的触发项。账本的 ¥9.085016 是已结算费用与保留费用之和，不等同于已实际结算支出。由于尚未取得线上运行包 SHA，当前仓库的源码路径交叉核对不能替代线上部署制品同一性的证明。

据 2026-11-16 只读查询记录，Neon 中共 41 条 P8 作业：24 条成功，17 条以 `permanent_failed` 结束；这 17 条的持久化错误码都是 `ModelBudgetExceeded`，作业尝试次数都是 3。逐作业统计 payload 数组长度后，成功的 24 条和失败的 17 条均为每批 4 条。这证明当前任务实际采用了“四条声明一批”的分批数据形态，但不能据此确定执行代码的提交 SHA 或线上运行包身份。失败窗口的 SCF 日志能看到同一总 Tokens 错误在重试中重复出现。

同日对数据库中的声明 ID 做了集合校验：P7 有 164 个唯一声明 ID；P8 作业 payload 合计包含 164 个唯一 ID；24 个成功结果包含 96 个唯一声明 ID；17 个失败作业 payload 包含剩余 68 个唯一 ID；成功结果与失败 payload 无重叠，P7 中没有成功 P8 结果的 68 个 ID 都在失败 payload 中。因逐作业 payload 统计已确认每批 4 条，所以 24×4=96 条已通过 P8 成功结果保存，17×4=68 条尚无成功结果。风险标签分布为：96 个成功结果含 27 high、10 low、59 medium；68 个未完成项含 40 high、2 low、26 medium。因而目前可确认仍缺少成功 P8 结果的是这 68 条声明，不会把已成功的 96 条误计为待重做。此集合校验仅证明 ID 覆盖与分区，不证明已成功内容的科学质量或 P9 可直接交付。

按 P8 的模型尝试预算账本汇总（包含已结算模型结果、缓存事件和未结算预留；不是作业数、批次数或声明数，且不能直接对应单个作业或队列 attempt）：Flash 有 258 条 accepted、68 条 cache_hit、3 条 rejected；Pro 有 115 条 accepted、15 条 cache_hit、7 条 empty_output、3 条 truncated、3 条 `budget_state=reserved`。3 条 Pro reserved 记录合计 `reserved_total_tokens` 75,368、`reserved_cost_cny` ¥0.511957。另 3 条 Flash rejected 记录的 `reserved_total_tokens` 合计 30,956、`reserved_output_tokens` 合计 16,164，结算费用合计 ¥0.023264。Pro accepted 记录为 `reserved_total_tokens` 1,640,120、`total_tokens` 722,717、结算费用 ¥5.234034。此处账本的 reserved 字段是调用前预算预留，不是实际使用 Tokens/费用；账本仍为 reserved 的记录曾成功建立预算预留，但不能据此判断是否已向模型服务发出请求、是否产生实际用量或为何未结算。该汇总说明阶段中存在返回无效/不完整结果和未结算预留，但不能据此判断它们分别属于哪一个失败批次或哪一次队列 attempt。

进一步读取 3 条 Pro reserved 明细发现：其账本 model attempt 均为 1，创建时间为 2026-11-13 11:13:47—11:45:49 UTC；早于最早 `permanent_failed` 作业时间（2026-11-14 05:10:08 UTC）约 17 小时。三条 `detail_json` 合计 6 字节（均为空对象 `{}`），没有作业/批次关联字段。时间先后说明它们不是在最终失败时段才新建的预留；但既不能据此判定它们属于某个更早的失败批次，也不能判定是否实际发往模型服务或产生了实际用量。

为补查请求关联，在腾讯 CLS 的 SCF Worker 日志主题中按三条账本 `request_id` 分别检索，并将时间限定在北京时间 2026-11-13 19:00—20:00（覆盖三条预留创建时间）。三条检索结果均为空。当前仓库的 Worker 错误日志格式不保证写入账本 `request_id`，也没有为每次供应商请求提供必达日志；因此该阴性结果只表示此日志主题/时间窗没有匹配记录，不能证明请求没有发出、没有计费或没有模型调用。由于线上包 SHA 尚未确认，也不能断言线上运行包采用了当前仓库的日志格式。这三条预留仍不能映射到具体 P8 作业、批次或队列 attempt，是否产生实际 Tokens/费用仍未确认。

按当前仓库实现，预算预留拒绝发生在对应模型 HTTP 请求之前；如果线上运行路径与该实现一致，与 SCF 预算错误逐次对应的被拒绝子请求不会产生模型调用费用。但这不足以证明整次队列 attempt 没有先前已成功发出的模型请求，因为 P8 一个作业可能在后续子请求被预算拒绝前已完成其他调用。目前的聚合账本没有按作业 attempt 关联这些请求，因此不能断言 17 个失败作业各自的 3 次队列尝试都没有新增付费调用，也不能从 `attempt=3` 推算出付费模型请求次数。现有汇总同样不足以判断 rejected、empty_output、truncated 记录中有多少引发了后续付费重试。

云函数当前环境显示 `MODEL_TASK_MAX_TOTAL_TOKENS=3000000`、`MODEL_TASK_MAX_COST_CNY=10`。三个独立的 Pro 限制变量未配置；但日志已经确认本次触发的是共享任务总 Tokens 上限。

## 影响上线的规则与实现问题

仓库中的《P8动态路由与成本保护规则》要求请求发出前保守预留任务 Tokens，并在超限时停止。这条硬限制阻止了会使账本保守计入 Tokens 超过 300 万上限的下一次模型请求。

需要修复的是错误处理：当前仓库中的生产 Worker 对作业执行中抛出的异常未按类型区分；只要当前 attempt 小于 3，就会按同一路径安排下一次尝试。在预算、预留状态和输入均未变化时，原样重试不会消除预算阻断，却会再次领取作业并再次报错。预算类异常应该进入可识别的预算暂停状态，保留已完成批次，等待预算或任务范围由产品决策处理；不能把预算暂停当作普通可重试失败。线上运行包 SHA 尚未确认，因此以上代码行为是仓库实现与日志相符的交叉证据，不是部署包同一性证明。

文档的 P8 规则限制的是模型调用层“最多一次付费重试”；当前仓库模型客户端按初次调用加最多一次重试执行。该规则没有覆盖队列层对整个作业的重试。当前仓库 Worker 又未按异常类型区分，导致预算预留拒绝仍被队列重复领取。预算预留拒绝本身不发起模型调用；但 P8 账本另有 3 次 rejected、7 次 empty_output、3 次 truncated，现有汇总不足以判断其中多少触发后续付费重试，也不能把这些状态映射到 17 个终态失败作业。文档应补充：预算预留拒绝不得自动重试；恢复时复用成功检查点，只处理未完成项，并留下明确的人工恢复记录。

## 对当前任务的处理边界

- 不重新运行任务，不重复生成已成功的 24 个批次。
- 不修改 300 万 Tokens 或 ¥10 上限，不释放 75,368 个仍保留的 Tokens。本报告只列出这 3 条 Pro 预留的阶段合计；账本 `request_id` 在对应 SCF Worker 日志主题和时间窗中均未检索到，本次仍未建立它们与具体 P8 job、批次或队列 attempt 的关联，也未确认请求是否实际发出。它们的时间早于最终失败窗口，`detail_json` 也没有关联字段。
- 现有 17 个失败批次的原请求已在当前 300 万上限下触发共享 Tokens 预算拒绝；在账本、输入和预留状态不变且没有应用缓存命中的情况下，原样冷启动重试仍会被阻断。要完成剩余 68 条 P8 核验，必须在不丢失质量与范围的前提下重新评估 P8 所需模型预算；P8 完成后仍需执行并验收 P9 确定性装配。预算是否提高由用户决定。当前证据不足以给出完成这 68 条声明所需实际 Tokens 的严格下界或上界。
- 线上环境变量已查阅，但尚未独立取得运行包 SHA 并与 GitHub 生产分支对齐。因此本地源代码或文档变化不能视为线上修复或已发布版本。

## 后续修复方案

1. 在代码和持久化状态中区分 `budget_blocked` 与普通失败：不自动重试，不将整项任务误标为普通故障，不清除已成功检查点。
2. 记录稳定、无敏感信息的预算拒绝原因（例如 `task_total_tokens`），并保留 SCF 原因日志与任务、阶段、作业、尝试的关联标识。
3. 校准队列失败次数与 P8 重试政策：预算拒绝零重试；模型请求只在文档允许的情形下最多一次付费重试。
4. 对齐文档、决策记录、部署分支和运行包 SHA；部署前先在本地做对应回归，未经批准不改线上环境变量或数据库作业状态。

本节为 2026-11-17 同一 Neon 查询快照的只读补充。任务总账按每行状态取 `settled` 的 `total_tokens/actual_cost_cny`、或 `reserved` 的 `reserved_total_tokens/reserved_cost_cny`，与逐行求和一致；75,368 个 Pro 预留 Tokens 已包含在 2,995,455 的任务计入预算总额中，不能再加一次。此为应用账本口径，不是供应商账单或已实际扣费金额。

- 全任务 settled：2,920,087 Tokens / ¥8.573059；reserved：75,368 Tokens / ¥0.511957；计入任务预算合计：2,995,455 Tokens / ¥9.085016。
- P8 settled：2,406,846 Tokens / ¥8.003689，其中 Flash 为 1,617,257 / ¥2.221688，Pro 为 789,589 / ¥5.782001。另有 Pro reserved 75,368 / ¥0.511957，因此 P8 计入预算合计为 2,482,214 Tokens / ¥8.515646。
- P8 结果状态分组中，Flash 有 68 条、Pro 有 15 条 `cache_hit`；这些行的 `total_tokens`、`actual_cost_cny` 和供应商 prompt-cache hit tokens 均为 0。结合当前仓库实现，这与应用层响应缓存命中相符；它们是历史零用量缓存返回，不代表供应商 prompt cache，也不证明剩余失败批次当前能命中缓存。
- 当前仓库的应用层响应缓存先于预算预留检查。若缓存文件存在、缓存键与任务/阶段/路由/模型/提示词/完整 payload 完全一致且输出通过 validator，该子请求可直接复用并记零 usage；供应商 prompt cache 则发生在请求发出后，命中的输入 Tokens 仍计入总 Tokens，只降低输入费用。上述代码结论受线上部署 SHA 未知这一边界约束。
- 应用响应缓存位于函数实例本地临时目录 `/tmp/model-response-cache`，不在 Neon/COS，也不保证跨冷启动、实例回收或部署存在。未来执行实例的临时缓存无法通过当前账本证明。因此预算方案不得预先假定会命中；只有确认当前执行实例存在对应精确 cache key 并通过 validator，才能把该子请求记作预计零新增 Tokens。
- 失败 P8 作业的完整持久化 payload 共 17 批、68 条声明，平均 JSON 文本长度约 255,726.5 字节，最大 256,262 字节。此 payload 包含共享来源/证据等数据；`verify_claims` 会按风险、路由、证据与复杂度重组动态子批次，`generate` 再基于重组后的实际请求估算输入。完整作业 payload 字节数不能直接换算模型输入 Tokens 或恢复预算。
- 不能把每次调用的 `max_tokens`/输出预留下限（如 Flash 1,200、Pro 6,400）乘以失败作业数，当成实际 Tokens 的消费下界：这些是请求前额度/预留，返回后按实际用量结算，未使用预留不会按额度逐次永久累加。当前可以确认的是，17 个失败作业的原请求已被共享预算拒绝；不能由此推导完成剩余 68 条所需的精确费用或 Tokens 上下界。单个未缓存 Pro 调用的 6,400 输出预留大于当时约 4,545 的剩余空间，但还需确认剩余路径确实路由到 Pro；Flash 请求是否能通过则需要具体动态子请求的输入预留和输出额度，现有完整 payload 字节数不足以判断。

## 2026-11-17 二轮根因排查：预算放大器与证据缺口

本节补充分阶段只读汇总、成功 P8 作业保存的路由 metadata，以及当前生产候选源码检查。源码结论仅代表相应 GitHub 分支；线上 `$LATEST` 的运行包 SHA 尚未取得，因此不把分支行为当成线上制品已证事实。

- 分阶段 settled 用量为：P2A 4,645 Tokens / ¥0.048512；P2B 8,099 / ¥0.015621；P3 43,044 / ¥0.050984；P4 25,333 / ¥0.046184；P5 44,767 / ¥0.082429；P6 282,077 / ¥0.151399；P7 105,276 / ¥0.174241；P8 2,406,846 / ¥8.003689。P8 占全任务 settled Tokens 的约 82.4%、settled 账本费用的约 93.4%；因此剩余预算被耗尽的主体是 P8 已结算用量，而不是 75,368 个未结算预留。费用是应用账本估算，不是供应商账单。
- 失败结果也产生了已结算用量：P2B 有 1 条 rejected、P5 有 1 条 empty_output、P6 有 6 条 rejected；P8 有 3 条 rejected、7 条 empty_output、3 条 truncated。P8 这 13 条共结算 83,036 Tokens / ¥0.571231，说明无效/不完整输出会形成实际账本消耗；当前聚合不能把这些请求关联到 17 个最终失败作业或某次队列尝试。
- 24 个成功 P8 作业持久化的 `metadata.routes` 合计记录 23 次 `high_risk / deepseek-v4-pro` 路由、覆盖 23 个 claim slots，以及 27 次 `standard / deepseek-flash` 路由、覆盖 73 个 claim slots。该成功作业集合中 Pro 覆盖数已超过配置说明的“Top 10”范围，强烈提示实际路由可能没有实施 Top 10 限制。它不能证明 17 个失败作业路由相同，也不能替代运行包 SHA 核对。
- 当前生产候选源码的 P8 编排未把 `pro_claim_ids` 放入作业 payload；路由函数在参数缺省时会将所有符合条件的中高风险因果/疗效/安全/审批类声明放入 Pro。配置文案则写着仅 Top 10 优先声明升 Pro。这是代码路径与策略文案的明确不一致；需用线上包 SHA 与任务 payload 再确认它是否解释了本次全部 115 条 Pro accepted 记录。
- 同一候选源码将 P8 Pro 输出额度设为 6,400—9,600，规则文档仍写 Pro 最高 3,200；P8 子调用的 `max_attempts=3`，规则文档“最多一次付费重试”对应的总调用上限为 2。两项都是文档与源码不一致，可能提高预留或失败重试消耗；不能据此断言线上包使用该版本或实际每项都重试到上限。P8 的 3 条 truncated Pro 记录合计正好使用 19,200 completion tokens，与每次 6,400 输出限制相符，但缺少逐请求/作业关联。
- 当前候选 Worker 对所有异常都按最多 3 次队列 attempt 重试，没有为 `ModelBudgetExceeded` 设置预算暂停/零重试分支。当前 Neon 快照中 24 个成功 job 是 attempt=1，17 个失败 job 是 attempt=3。若后续动态子批失败，`verify_claims` 不会返回完整结果，Worker 也不会保存该作业的部分结果为数据库检查点；外层重试可能重做较早完成的子批。实例 `/tmp` 应用响应缓存可能在同一热实例减少重复请求，但不保证跨冷启动或换实例。
- 恢复入口会把失败 job 的 `attempt` 重置为 0、清空作业结果，但不会清除模型账本。因此当前 `attempt=3` 不是任务生命周期总执行次数；可能存在前次恢复周期，也可能存在其他 P8 入口/制品版本。P8 账本目前有 373 条 accepted（Flash 258 + Pro 115），不能仅按当前 `attempt` 快照分配到作业或恢复周期；该计数本身不能判定是否发生过人工重跑、也不能给出各失败作业的已付费调用数。
- 版本形态仍有明显缺口：数据库中 41 个 P8 job 的 payload 均为 4 条声明；当前生产候选编排路径生成单个完整 P8 job，另一条蓝绿 stage-transition 路径的批量常量是 6。当前这两条源码路径都解释不了观察到的 `41×4` 形态，进一步支持“线上制品/入口/恢复操作未对齐”是首要待查项，但还不能单凭形态判断究竟是哪条旧版本或手工路径生成了这些 job。
